# ADR-0004 — Secrets model

## Status

Accepted, 2026-07-25.

## Context

The platform handles several classes of secret:

1. **Operator WireGuard private key.** Generated on the
   operator's workstation, never leaves the workstation.
2. **Bastion WireGuard server private key.** Generated on
   first boot of the bastion, never leaves the bastion.
3. **Per-lab application secrets** (database passwords,
   WordPress salts, etc.). Generated by the platform per
   lab, never leave the lab.
4. **Operator dynamic-IP updates.** The operator's current
   public IPv4 is added to and removed from the bastion
   firewall allowlist at runtime. This is operational state,
   not a secret.

The platform must keep secrets out of Git, Terraform
variables, Terraform state, VM metadata, startup scripts,
console output, issue comments, and logs.

## Decision

### Operator WireGuard private key

The operator generates the keypair on their workstation:

The operator generates the keypair on their workstation
using their platform's WireGuard tooling (typically
`umask 077` plus a single command that emits both keys),
stores the files with mode `0600`, and ships the private
key only through a secure channel of the operator's
choice. The exact command line depends on the operator's
distribution and is not reproduced here.

The platform receives only the contents of
the operator's public key file. The private key is never transmitted
to the platform. The operator ships the operator's private key file
to themselves by their preferred secure channel (encrypted
USB, password manager, secure shell transport). For an
operator who wants the platform to manage the key, an
explicit exception is recorded as a deviation; the key is
then stored at the path supplied by the
`BBR_WG_PRIVATE_KEY_FILE` environment variable (mode `0600`,
owner equal to the operator's primary group).

### Bastion WireGuard server private key

Generated on first boot by `cloud-init`. Stored at
`/etc/wireguard/wg0.key`, owner `root:root`, mode `0600`.
Never copied to Terraform, metadata, or any other system.

### Per-lab application secrets

Generated by the platform using `openssl rand -hex 32` (or
equivalent). Stored at `/etc/bbr/<lab-id>/secrets/` on the
appropriate lab VM, mode `0600`. Never written to Terraform
variables, Terraform state, the lab manifest, or scenario
output.

### Dynamic-IP allowlist updates

The operator runs the procedure documented in
`DIRECTIVE.md` Section 16. The platform provides a helper
script, `scripts/update-firewall-cidr.sh`, that:

1. Reads the current allowlist.
2. Adds the operator's current public IPv4.
3. Writes the new allowlist back to the bastion firewall.

The helper requires `roles/compute.securityAdmin` on the
platform project. The platform itself does not perform this
operation; the operator does. This is by design — the
operator's current IPv4 is not visible to the platform.

### Redaction at the runner

Scenarios may capture sensitive output (for example,
database dumps, error logs). The runner applies a redaction
policy to every captured artefact before writing to the
evidence store. The redaction policy is part of the lab
pack (see `evidence_sources[].kind`).

### Disposal

`bbr destroy` removes the lab's resources. The
`/etc/bbr/<lab-id>/secrets/` directory is shredded (`shred
-u` on each file) before being removed. The platform does
not retain any record of the per-lab secrets after destroy.

## Consequences

- A compromised platform repository reveals no secret
  material.
- A compromised Terraform state reveals no secret material
  beyond resource IDs and CIDR allocations.
- An operator who loses their private key must re-issue
  the lab pack.
- A lab VM that is captured during a window between lab
  creation and `bbr isolate` may still reach the bootstrap
  allowlist. The bootstrap allowlist is therefore reviewed
  by the operator before each `bbr create`.

## Alternatives considered

- **Vault / GCP Secret Manager.** Rejected for v1 because
  it adds a service dependency and a cross-cutting
  permission model. A future version may integrate.
- **Encrypted secrets in Terraform state.** Rejected because
  it forces the operator to manage the encryption key
  outside the platform.
- **Long-lived SSH keys for operator-to-bastion access.**
  Rejected because IAP TCP forwarding provides the same
  capability without a long-lived secret.
